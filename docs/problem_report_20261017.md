# Omega-Uzu 문제점 리포트 (2026-10-17)

이 문서는 지금까지의 측정과 코드 검사를 바탕으로, Omega-Uzu를 uzu와 경쟁
가능한 상태로 만들기 위해 막고 있는 문제를 정리한다. 각 항목은 근거 수치,
확인한 범위, 그리고 어드바이저의 판단이 필요한 결정을 담는다.

측정 환경: Apple M5 Pro 48GB, macOS 27.0, Xcode 27.1, uzu 릴리스 0.6.9,
`trymirai/Qwen3.5-9B-M` (Mirai-M 4비트, 가중치 파일 5,189,121,136 바이트).

## 요약: 한 문장

> Omega-Uzu는 검증된 비트 포맷과 48.4% 바이트 감소를 계산으로 증명했지만,
> 실제 체크포인트를 만들어 디코드하는 경로가 없고, 같은 shape의 GEMV 처리량은
> uzu보다 5.1-6.9배 낮다.

## 문제 1 (최상위): 모델 변환이 불가능하다

### 무엇이 없는가

KSC 포맷으로 실제 모델을 변환하는 경로가 없다. 저장소의 유일한 인코더는
`ksc_curvetq_quantize_row` 이고, 이 함수는 `raise ValueError("reference Viterbi is
exact only for block <= 6")` 로 블록 6열 이하만 받는다. 생산 블록은 64열이다.

따라서 Phase A(오프라인 변환)의 어떤 단계도 실제 규모에서 실행된 적이 없다:

| Phase A 단계 | 참조 구현 | 생산 규모 실행 |
|---|---|---|
| 크로네커-헤시안 프로파일링 | CASA 폐쇄형 존재 | 캘리브레이션 미연결 |
| 슈어 보수 + LDL | 소행렬 검증됨 | 64열 블록 변환 없음 |
| 곡률 비터비 (2비트 + s0*) | 블록 <= 6 전용 | **불가** |
| StagQ + AWSRC 생성 | 소행렬 검증됨 | 모델 미적용 |
| OptR 회전 병합 | 함수 존재 | 모델 미적용 |
| 변환된 체크포인트 저장 | – | **불가** |

### 왜 이것이 최상위인가

다른 모든 문제의 전제다. 인코더가 없으면 bpw 절감도, 품질 측정도, 종단 tok/s도
측정할 수 없다. 지금까지 만든 커널·파리티·처리량 측정은 모두 합성 입력이다.

### 판단이 필요한 것

- 비터비를 64열로 확장할 것인가, 아니면 논문의 정확 최소화를 포기하고 근사
  (예: 코드북 독립 최적화 + 슈어 곡률 가중 유클리드)로 갈 것인가?
- 확장 시 탐색 공간은 2^(2x64) 이므로 완전 탐색이 불가능하다. 빔 서치 폭, 반복
  횟수, 허용 시간 예산을 어떻게 정할지 결정이 필요하다.

## 문제 2: 처리량이 uzu의 1/5 수준이다

### 측정값

| 커널 | Shape | 가중치 처리량 |
|---|---|---|
| 스칼라 (스레드당 1행) | K=64 | 25.8-38.7 GB/s |
| SIMD 그룹당 1행 | N=12288, K=4096 | 51.6 GB/s 최고 |
| uzu 디코드 실효 | 실제 9B 모델 | 261-354 GB/s |
| 기기 float4 피크 | – | 188-417 GB/s (실행별 변동) |

격차 5.1-6.9배. 세 번 반복에서 49.7/51.6/50.8 GB/s로 안정적이었다.

### 원인

포맷이 아니라 산술 집약도다. KSC GEMV는 코드 16바이트당 MAC 64개(약 2.7 MAC/byte)를
만들고 측정 피크의 13%에 그친다. uzu의 `gemm_trellis`는 한 번의 로드로 MMA 타일
전체를 채워 69-93%에 도달한다.

### 판단이 필요한 것

- uzu의 fragment 로더(`mxu_mma`)에 맞춰 KSC 코드 레이아웃을 재배치하는 이식이
  필요한데, 이는 uzu 포크 + nightly Rust 빌드를 뜻한다. 착수할 가치가 있는가?
- 아니면 GEMV 경로를 배치 1 전용으로 인정하고, uzu가 프리필에서만 배치 GEMM을
  쓰는 구조를 따라 이득이 없는 것으로 결론지을 것인가?

## 문제 3: 품질이 전혀 측정되지 않았다

2.38075 bpw가 정확도를 유지한다는 주장은 arXiv 참조 논문(StagQ, AWSRC, CurveTQ)에
기대고 있고, 이 저장소에서 확인한 적이 없다. 속도만 측정된 상태다.

선행 조건: 문제 1(인코더)이 해결되어야 측정 가능하다.

### 판단이 필요한 것

- 품질 기준을 무엇으로 둘지: perplexity, 아니면 과제 정확도(예: MMLU 일부),
  아니면 uzu 출력과의 토큰 일치율?
- 비교 기준선: uzu Mirai-M 4비트(현재 실측 9B 약 55 tok/s)와 동일 프롬프트 세트.

## 문제 4: uzu 통합이 문서상 계약으로만 존재한다

`docs/uzu_metal_kernel_mapping.md` 는 3개 통합 지점의 계약을 정의했고,
`metal/` 팩이 그중 넷을 실측으로 검증했다. 그러나 uzu 저장소는 수정되지 않았다.

uzu HEAD `5baa58b7`(2026-10-17) 확인 결과:

- 있는 것: `gemm_trellis`, `weaver`, `gdn/tree_verify` 커널
- 없는 것: AWSRC, ReadKV, LiLiCorr 커널

### 판단이 필요한 것

- 포크를 만들 것인가, 아니면 upstream에 PR로 제안할 것인가?
- uzu는 하루에도 HEAD가 이동한다(확인일 하루 전 커밋). 포크 유지 비용을
  감당할 것인가?

## 문제 5: 투기 경로가 대역폭의 27-32%만 쓴다

이것은 uzu의 문제이고 Omega-Uzu의 기회다.

측정: 투기 ON 경로는 유효 109-119 GB/s를 쓰고, 기기 피크는 188-417 GB/s다.
투기 OFF는 261-354 GB/s를 쓴다(투기가 오히려 대역폭을 덜 쓴다).

즉 현재 9B 대화 모드(중간값 56.97 tok/s)와 투기 OFF(54.99 tok/s)가 거의 같다.
트리 검증 비용이 수락 이득을 상쇄한다.

### 이미 확보한 근거

실측 패스 비용 피팅(단일 패스 18.19 ms, 16슬롯 검증 47.40 ms = 고정 16.10 ms +
후보당 2.086 ms)으로 계산한 최적 budget은 3-4이고, 이득은 1.77-2.12배다.

제약: `speculator/shapes.json` 을 편집하면 엔진이 그 파일을 삭제하고 로드가
실패한다. budget 변경은 엔진 코드 또는 설정 경로가 필요하다.

### 판단이 필요한 것

- 이 최적화(1.77-2.12배 예측)를 먼저 실측 검증할 것인가, 아니면 Omega-Uzu
  인코더(문제 1)에 집중할 것인가?
- budget 변경 지점을 찾기 위해 uzu 소스 수정이 필요한데, 이는 문제 4와 묶인다.

## 문제 6: 참조 커널과 계약 문서의 정합성

경미한 항목이지만 기록한다.

- `omegahee_pillars.py` 의 `readkv_mean_bits` 와 `project_single_pass_tps` 는
  `metal/tools/roofline.py` 에서 호출된다(이전에 미사용이던 항목은 해소됨).
- 비교 문서의 두 수치는 이번에 정정했다: 격차 3배는 더 작은 스칼라 커널 기준이었고
  동일 shape에서는 5.1-6.9배다. float4 피크는 단일 값이 아니라 188-417 GB/s 범위다.

## 현재 증명된 것 / 증명되지 않은 것

증명됨:

- KSC 코드 스트림의 랜덤 액세스 성질(레인 l = 니블 l), 32행 전부에서 직렬 결과와 일치
- 파리티 게이트 5종의 numpy 일치(최대 오차 1.43e-06 ~ 7.45e-08). 처리량 프로브 3종은 측정 전용이다.
- 2.38075 bpw 산술과 48.4% 바이트 감소(계산)
- uzu 실측 베이스라인: 9B 투기 OFF 50.3-68.2 tok/s, 투기 ON 55.1-71.2 tok/s
- 패스 비용 피팅과 최적 budget 3-4(모델)

증명되지 않음:

- 2.38 bpw의 품질
- 종단 tok/s (경로 자체가 없음)
- 처리량 우위 (5.1-6.9배 열세)
- 실기기 budget 변경 실험

## 어드바이저에게 묻는 것 (우선순위 순)

1. 인코더 전략: 64열 비터비를 근사로 대체할지, 빔 서치로 확장할지, 아니면
   Phase A를 lalamo 파이프라인에 위임할지.
2. 착수 순서: 인코더(문제 1) vs uzu 이식(문제 2, 4) vs budget 검증(문제 5).
   현재 근거로는 budget 검증이 가장 저렴하고(측정만 필요), 인코더가 가장
   큰 병목이다.
3. 품질 기준과 기준선 설정.
4. uzu 포크 여부와 유지 비용 수용 범위.
