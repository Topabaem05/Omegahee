# Dory 하이브리드 루프 실험 계획 (2026-10-19)

근거 문서: "Dory 하이브리드 루프 설계 계획서"(2026-10-19, 선택안 B: 코어 잠재 루프). 이 계획은 설계를 학습에
들어가기 전에 검증할 실험과 순서를 정합니다. 실험 ID는 `H-xx`이고, 결과는 `docs/dory_research_log.md`와 같은
형식으로 기록합니다.

## 1. 설계 전제 확인 결과

설계 문서의 전제를 현재 엔진·모델과 대조했습니다.

| 전제 | 확인 결과 | 영향 |
|---|---|---|
| 예약 토큰 `<SPECIAL_N>`(ID 18~507) 중 두 개를 `<latent>`, `</latent>`로 씀 | `tokenizer_config.json`에 `<SPECIAL_18>`~`<SPECIAL_999>` 982개가 있음. `<think>` 12, `<tool_call>` 14, `<tool_response>` 16도 있음 | 문제 없음. 범위는 18~999 |
| KV 모드는 `last_loop`로 고정 | 변환 기본값은 `per_loop`. `last_loop`는 prefill에서만 `per_loop`와 같고 decode에서는 다름(전체 재계산 대비 로짓 차이 0.2~17, `docs/dory_stage0_reference_20261019.md`). `last_loop` decode의 품질 묶음 점수는 잰 적이 없음 | **가장 먼저 확인할 위험(H-01)** |
| 텍스트 속도 약 100 tok/s(INT4 상한) | 현재 권장 구성(NVFP4 FP8 스케일 + readout INT4)은 `per_loop` wavefront 91.35, 순차 69.61 tok/s. wavefront는 `per_loop`만 지원 | `last_loop`로 바꾸면 wavefront를 다시 만들어야 텍스트 속도가 유지됨(H-02) |
| 잠재 스텝 약 1.04GB, 약 295 스텝/s | 코어 40층 FP4 1.03GB + 잠재 링크(BF16) 26MB, 대역폭 상한 약 290 스텝/s. 측정한 커널 시간으로 어림하면 약 5.6ms, **약 180 스텝/s** | 아래 표 |
| 잠재 스텝/s가 텍스트 tok/s의 2.5배 이상 | 어림값 180 스텝/s는 wavefront 텍스트(91.35)의 약 2.0배, 순차 텍스트(69.61)의 약 2.6배 | 성공 기준의 텍스트 기준선을 정해야 함(H-03) |
| 64GB 이상 Mac에서 T2 예비 학습 가능 | 이 기기는 48GB | T2 예비 학습은 메모리 확인 후 결정(H-08) |

잠재 스텝 시간 어림(현재 엔진, 2K 문맥, m=1):

| 부분 | 근거 | 시간 |
|---|---|---|
| 코어 선형층 GEMV | FP4 마이크로벤치 20 × (qkvg 51.1 + out 20.1) + 20 × (up 71.4 + down 35.9)µs × 모델 안 보정 1.15 | 4.11ms |
| 코어 attention 20회 | wavefront pass의 attention 1.87ms ÷ 56 dispatch | 0.67ms |
| 작은 커널(norm, 잔차 mix) | pass당 1.10ms ÷ 72 하위층 × 40 | 0.61ms |
| 잠재 링크 + 종료 프로브 | BF16 26MB를 약 250GB/s로 읽음 + norm | 0.16ms |
| 합계 | | 약 5.55ms(약 180 스텝/s) |

wavefront는 텍스트 토큰도 코어를 토큰당 한 번만 읽게 합니다. 그래서 잠재 스텝이 아끼는 것은 입력·출력 그룹과
readout(약 1.1GB)뿐이고, 바이트 비는 3배가 아니라 약 2.1배입니다.

## 3. 실험 목록

### H-01 `last_loop` 품질 기준선 (Mac, 엔진, 학습 없음)

- 목적: 설계가 고정한 `last_loop`가 Dory 품질을 지키는지 본다.
- 방법: 권장 구성(`nvfp4-r4-fp8s`)을 `kv_cache_mode`만 바꿔 두 벌 만들고, 순차 decode로 품질 묶음(GSM8K 200,
  HumanEval 164, MMLU-Pro 500, 16K 검색 20)을 잰다. teacher-forced KL(BF16 `per_loop` 기준)도 같이 잰다.
- 판정: `last_loop` 점수가 `per_loop`보다 1%p 넘게 낮거나 BF16의 97% 아래면 A1 실패. 이때 설계에 "`per_loop`에서
  잠재 위치 KV를 1루프 슬롯에 쓰는" 변형을 추가로 제안한다.
- 비용: 변환 수 분, 품질 묶음 2회 약 2.5시간.

### H-02 `last_loop` wavefront (Mac, 엔진 구현)

- 목적: 하이브리드 모델의 텍스트 모드 속도를 지킨다.
- 방법: `last_loop`에서는 토큰 t의 2번째 루프와 t+1의 1번째 루프가 같은 KV 상태를 쓰므로, 두 행을 행 묶음 둘이
  아니라 인과 마스크가 있는 2행 하나로 돌린다(t의 KV를 먼저 쓰고 t+1이 읽음). 1루프 조기 종료 추측과 미리 인코딩
  (E-07)은 그대로 쓴다.
- 검증: 추측을 모두 맞은 경우 순차 `last_loop` decode와 같은 토큰(teacher-forced logits 차이 BF16 수준), 요청 묶음
  생성 문장 비교.
- 판정: 2K decode가 `per_loop` wavefront의 98% 이상이면 채택.
- 비용: 구현과 검증 약 1일.

### H-03 잠재 스텝 비용 시제품 (Mac, 엔진 구현, 학습 없음)

- 목적: A3을 실측하고, 성공 기준의 텍스트 기준선을 정한다.
- 방법: `Decoder::encode_latent(prev_state)`를 만든다. 잠재 링크는 `W_down = 0`(항등 링크), 종료 프로브는 0 가중치로
  두고, 코어 1회(변형: 2회)만 돌린다. 잠재 위치는 코어 attention 20층에만 KV를 쓴다. 128, 2K, 16K 문맥에서 연속 잠재
  스텝 200개의 스텝/s를 잰다. 종료 프로브 값 하나만 CPU로 읽고 다음 스텝을 미리 넣는 방식(설계 uzu 5항)도 같이 잰다.
- 판정: 어림값(약 180 스텝/s)과 비교한다. 성공 기준 "잠재 스텝/s ≥ 텍스트 tok/s의 2.5배"를 순차 텍스트 기준으로 둘지
  wavefront 기준으로 둘지 결과와 함께 정한다(wavefront 기준이면 현재 어림으로는 약 2.0배라 미달).
- 비용: 약 1일.

### H-04 무학습 잠재 연속성 (Mac, 참조 PyTorch 또는 엔진 하네스)

- 목적: T2의 출발점을 잰다(A4, A5의 무학습 기준).
- 방법: BF16이 생성한 답(품질 묶음 GSM8K 50개)을 텍스트로 넣어 위치별 코어 최종 상태 `c_j`를 얻는다. 같은 구간을
  항등 링크로 `s_j = core(s_{j-1})`처럼 이어 돌려 다음을 잰다.
  - 스텝별 `cos(s_j, c_j)`(설계 T2 손실의 무학습 값)
  - `s_j`를 출력 그룹과 `lm_head`에 통과시킨 다음 토큰 top-1 일치율(LOTUS식 읽어내기의 무학습 값)
  - 상태가 고정점으로 수렴하는지(스텝 간 cos)
- 판정: 수치 자체가 기준선이다. 구간 끝 텍스트 스텝의 로짓이 잠재 구간을 텍스트로 넣었을 때와 얼마나 다른지(KL)도
  재서, 출력 그룹이 잠재 위치를 못 보는 비용(A5)을 학습 전 값으로 남긴다.
- 비용: 약 0.5일.

### H-05 층 그룹별 KV와 전역 위치 슬라이딩 마스크 (참조 → lalamo → 엔진)

- 목적: 설계의 KV 규칙(입력·출력 그룹은 잠재 위치를 건너뜀, 슬라이딩 윈도는 전역 위치 차이로 판단)을 학습 코드(T0)와
  엔진이 같게 구현한다.
- 방법: `reference/dory_ref.py`에 위치 존재 벡터와 전역 위치 마스크를 먼저 넣는다. 잠재 위치가 없으면 기존 출력과
  비트 단위로 같아야 한다. 그다음 lalamo tracer, uzu CPU, uzu Metal 순서로 같은 규칙을 넣는다.
- 검증: 잠재 위치가 섞인 고정 입력 몇 개에서 네 구현의 텍스트 로짓이 허용 오차 안에서 같음. 슬라이딩 윈도 경계를 넘는
  입력을 포함한다.
- 비용: 참조 0.5일, 엔진 1~2일.

### H-06 Dory 루프 수와 거절 (Mac, 엔진, 학습 없음)

- 목적: "루프를 줄이면 거절이 약해진다"는 결과가 Dory에도 맞는지 보고, 하이브리드 안전 기준선을 남긴다(A6).
- 방법: 유해 요청 묶음과 무해하지만 경계에 있는 요청 묶음으로, 텍스트 루프 1·2·3회 × `per_loop`·`last_loop`에서 거절률과
  과잉 거절률을 잰다. 판정은 규칙 기반 거절 표지 + 표본 수작업 확인으로 한다.
- 필요: 평가용 요청 묶음(공개 데이터 선택과 라이선스 확인은 사용자 결정).
- 비용: 데이터 준비 후 약 0.5일.

### H-07 학습 데이터와 계산량 점검 (Mac)

- 목적: 클라우드 학습 예산을 실제 데이터로 다시 계산한다(A7).
- 방법: HybridSFT-v2의 라이선스, 크기, 궤적 수를 확인하고, Dory 토크나이저로 다시 토큰화해 궤적 길이 분포, 잠재 구간
  길이 분포, 도구 태그 변환 실패율을 잰다. 이 값으로 T1~T4의 FLOPs와 H100 시간을 다시 어림한다.
- 필요: 데이터 내려받기 승인.
- 비용: 약 0.5일.

### H-08 T2 소규모 예비 학습 (Mac 가능성 확인 후)

- 목적: 링크·프로브만 학습해도 H-04 기준선보다 나아지는지 학습 전에 본다(A4, A5).
- 방법: 교사는 원본 Dory(T1 생략)의 코어 상태로 한다. 링크와 프로브(약 1,300만 개)만 학습하고, 코어를 통한 역전파는
  8스텝으로 자른다. 먼저 48GB에서 메모리가 맞는지(BF16 백본 약 8GB 고정, 코어 40층 활성값) 1스텝으로 확인한다.
- 판정: 보조 cos와 읽어내기 정확도가 H-04보다 뚜렷이 좋아지면 클라우드 T1~T4로 넘어갈 근거로 쓴다. 메모리가 안 맞으면
  클라우드 1노드로 옮긴다.
- 비용: 1~2일.

## 4. 순서와 판정 지점

1. **H-01, H-03, H-04를 먼저**(서로 독립, 학습 없음). 설계 전제 셋(A1, A3, A4)을 하루 안에 확인한다.
2. **판정 G1**(H-01 뒤): KV 모드를 정한다. `last_loop`가 통과하면 H-02로, 실패하면 `per_loop` 잠재 위치 변형을 설계에
   제안한다.
3. **판정 G2**(H-02, H-03 뒤): 효율 성공 기준의 텍스트 기준선(wavefront 또는 순차)을 정하고, 잠재 스텝 비용이 목표에
   맞는지 본다.
4. H-05는 G1 결과에 맞춰 진행한다(학습 코드 T0의 핵심이기도 하다).
5. H-06, H-07은 데이터 승인이 나면 병행한다.
6. **판정 G3**(H-07, H-08 뒤): 클라우드 학습(T0~T4, H100 8장 1노드) 진행 여부와 예산을 사용자와 정한다.

## 6. 속도 연구와의 관계

- 하이브리드 설계는 텍스트 decode 경로를 바꾸지 않으므로, E-xx 속도 실험의 결과(FP4 GEMV, wavefront 등)가 그대로
  쓰인다. 다만 KV 모드가 `last_loop`가 되면 wavefront를 H-02로 다시 맞춰야 한다.
- 잠재 스텝은 코어 GEMV가 시간의 약 3/4이라, FP4 GEMV 개선이 잠재 모드에도 그대로 이어진다. 작은 커널 합치기(E-24 등)는
  잠재 스텝에서 비중이 더 크다(40층 중 작은 커널 약 0.6ms).
- E-24(QKV norm을 attention prepare에 합침)는 구현과 검증(CPU·Metal 비트 단위 일치, 생성 문장 동일)을 마쳤고, 다른
  세션의 CPU 작업 때문에 속도는 아직 재지 못했다(커밋 전).
- 측정 환경: 같은 기기에서 다른 세션이 CPU 작업을 반복해 돌리면 decode가 약 9% 낮게 나온다. H-01~H-03의 속도 측정은
  조용한 시간에 하거나, 짝지은 A/B로 상대 비교만 한다.
