# 27B가 20 tok/s인 이유와 메모리·MTP 최적화 (2026-10-18)

## 한 줄 요약

20 tok/s는 GPU가 느려서가 아니다. IQ1_S 디코드 커널이 **123GB/s**만 쓰고,
`llama-cli`가 기본으로 **262,144 토큰 컨텍스트(16GB KV)** 를 잡기 때문이다.
컨텍스트를 4,096으로 줄이고 MTP 투기를 붙이면 같은 모델에서 상대 속도가
**1.47배** 올라갔다(측정 중 다른 GPU 작업이 95% 점유한 조건).

## 왜 20 tok/s인가

27B는 배치 1 디코드에서 토큰마다 가중치를 한 번 읽는다. IQ1_S는 6.19GB이므로
366GB/s에서 이론 상한이 59 tok/s다. 실측 19.87 tok/s는 50.3ms/token이고,
실효 대역폭은 123GB/s다. 즉 **대역폭의 3분의 1만 쓰고 있다.**

| 변형 | 파일 GB | tok/s | 실효 GB/s | 366GB/s 대비 |
|---|---:|---:|---:|---:|
| Mirai-M 4비트 (uzu) | 15.57 | 23.21 | 337-361 | 92-99% |
| Q4_0 (llama.cpp) | 16.06 | 13.21 | 212 | 58% |
| Q2_K_XL | 9.83 | 14.97 | 147 | 40% |
| IQ2_XXS | 7.27 | 18.68 | 136 | 37% |
| IQ1_S | 6.19 | 19.87 | 123 | 34% |

원인은 1.56bpw 언패킹 비용이다. IQ1_S는 바이트를 덜 읽지만, 가중치마다
코드북 조회와 비트 언패킹이 필요해 GPU가 메모리 대기 대신 ALU에서 막힌다.
Q4_0는 더 단순한 니블 언패킹이라 212GB/s, uzu의 4비트 trellis는 MMA로
디퀀트를 분산해 337-361GB/s를 낸다. **비트폭보다 커널의 산술 집약도가
더 큰 변수**다.

## 숨은 메모리 낭비: 기본 16GB KV

`llama-cli`는 `-c`를 생략하면 모델의 학습 컨텍스트(262,144)를 잡는다.
Qwen3.8-27B는 16개 full-attention 레이어에 KV 캐시를 만들므로 이것이
**16,384 MiB**가 된다.

| 실행 | 컨텍스트 | KV | 최대 RSS |
|---|---:|---:|---:|
| 기본 `llama-cli` | 262,144 | 16,384 MiB | **23.42 GB** |
| `-c 1024` | 1,024 | 64 MiB | **6.79 GB** |
| `-c 4096` | 4,096 | 256 MiB | **6.52 GB** |
| `-c 4096` + MTP n=4 | 4,096 | 256 + 16 MiB | **8.55 GB** |

기본값 대비 **16.6GB**를 절약한다. 이 여유는 macOS가 다른 앱과 모델 페이지를
스왑하지 않게 해 주므로, 단순 메모리 절약 이상의 속도 안정성을 준다.

## MTP 투기 디코딩

llama.cpp 0.7.0은 Qwen3.8의 `draft-mtp`를 지원한다. 1.37GB MTP 헤드를
`-md`로 붙이고 `--spec-draft-n-max`를 조절한다.

측정 조건: IQ1_S, `-c 4096`, 64토큰, greedy, reasoning off, 3라운드 교차.
**주의:** 측정 중 다른 YOLO 학습이 GPU를 95% 점유했다. 절대값은 오염됐고,
아래 상대 비교만 유효하다.

| 구성 | 중간 tok/s | 표준편차 | 평균 수락 길이 | RSS | 기준 대비 |
|---|---:|---:|---:|---:|---:|
| MTP 없음 | 9.70 | 0.80 | 1.00 | 6.52 GB | 1.00x |
| MTP n=2 | 12.10 | 0.61 | 2.30 | 8.26 GB | 1.25x |
| MTP n=3 | 13.40 | 0.61 | 2.70 | 8.40 GB | 1.38x |
| MTP n=4 | **14.30** | 1.21 | **2.95** | 8.55 GB | **1.47x** |

위치별 수락률은 `(0.826, 0.478, 0.391)`이었다. n=4의 평균 수락 길이 2.95는
“포워드 한 번에 2.95토큰”을 뜻한다. 그런데 속도 이득은 1.47배에 그친다.
4토큰 검증 포워드가 1토큰 포워드의 약 1.76배 비용이기 때문이다. Qwen3.8의
선형 어텐션(GDN) 재귀 상태가 후보 검증을 완전히 병렬화하지 못하는 구조다.

깨끗한 조건의 기준선 19.87 tok/s에 같은 1.47배를 적용하면 약 **29 tok/s**가
예상된다. 이는 Mirai-M의 23.2 tok/s를 넘는 값이지만, GPU 경합이 없는
재측정으로 확인해야 한다.

## 권장 실행

```bash
# 대화/생성: 4k 컨텍스트 + MTP
./tools/run_q27b_fast.sh -p 'Explain how attention works.' -n 256 --temp 0

# MTP 없이 비교
MODE=base ./tools/run_q27b_fast.sh -p 'Explain how attention works.' -n 256

# 메모리·속도 A/B 3라운드
.venv/bin/python tools/q27b_mtp_bench.py \
  --target ~/models/qwen38-27b/Qwen3.8-27B-UD-IQ1_S.gguf \
  --mtp ~/models/qwen38-27b/mtp-Qwen3.8-27B-Q4_0.gguf \
  --context 4096 --tokens 64 --rounds 3 --n-max 2,3,4 \
  --out bench/q27b_mtp_20261018.json
```

장문 컨텍스트가 필요하면 `CTX=32768`처럼 올린다. 32k에서도 KV는 2GB다
(262k의 16GB와 비교). 4k는 일반 대화에 충분하고, 1k는 메모리를 더 아낀다.

## 남은 확인

1. GPU가 유휴일 때 MTP n=4의 절대 tok/s를 3라운드 재측정한다.
2. MTP 수락률을 프롬프트 유형별로 본다(코드/설명/반복). 위 수치는 설명문 1개다.
3. `draft-mtp`와 `ngram-mod`를 함께 켜서 수락 길이가 더 늘어나는지 본다.
4. uzu Mirai-M에도 같은 small-context 설정이 있는지 확인한다(uzu는 별도
   `--cache-type`/컨텍스트 옵션이 있을 수 있다).
