# Dory 하이브리드 루프 실험 기록

계획: `docs/dory_hybrid_loop_experiment_plan.md`. 모델: NVFP4 FP8 스케일 + readout INT4(`nvfp4-r4-fp8s`), 2루프.
`last_loop` 변형은 같은 가중치에 `recurrence.kv_cache_mode`만 바꾼 설정입니다.

## 엔진 시제품 (H-03, H-04 공통)

- `encodable_block/transformer/hybrid.rs`(시험 빌드 전용): 잠재 스텝(recurrent 블록만, 입력 `u`에서
  `norm(u + u) = u`로 시작해 `loops`회), 코어 최종 상태를 함께 돌려주는 텍스트 스텝, 출력 층 읽어내기(KV 미확정).
  잠재 위치에서는 recurrent 층만 KV를 쓰고 입력·출력 층은 건너뜁니다. RoPE는 전역 위치를 씁니다.
- `unit/session/dory_hybrid.rs`(`UZU_DORY_HYBRID` 지정 시에만 실행): 잠재 링크
  `u = norm(s + W_down silu(W_up s))`(BF16, `W_down = 0`이라 항등)와 종료 프로브(BF16 GEMV)를 붙여 H-03, H-04를
  잽니다.
- 검증: 하이브리드 텍스트 스텝이 `Decoder::encode`와 로짓까지 같음(첫 프롬프트 32토큰, 최대 차이 0). 구간 시작
  상태의 읽어내기가 교사의 다음 토큰과 99.2% 같음(118개 중 117개).

## H-04 무학습 잠재 연속성 (2026-10-19)

GSM8K 24문항(질문은 `omega_eval.py` 프롬프트와 Dory 채팅 템플릿(추론 끔), 답은 BF16 모델의 답,
`bench/hybrid/h04_prompts.json`)을 한 토큰씩 넣어 위치마다 코어 최종 상태 `c_j`를 얻고, 48토큰마다 다음 16위치를
항등 링크 잠재 스텝으로 바꿨습니다(118구간, 문맥 1,000토큰 미만이라 슬라이딩 윈도 경계 없음).

| 지표(16스텝 범위) | `last_loop` | `per_loop` |
|---|---|---|
| 잠재 상태와 교사 상태의 cos | 0.975~0.981 | 0.976~0.981 |
| 기준: 구간 시작 상태와 교사 상태의 cos | 0.974~0.980 | 0.974~0.980 |
| 잠재 스텝 사이 cos | 0.997 → 1.000 | 0.997 → 1.000 |
| 잠재 상태 읽어내기가 교사 다음 토큰과 같음 | 1~7% | 1~8% |
| 교사 상태 읽어내기가 교사 다음 토큰과 같음(출력 층은 구간 위치를 못 봄) | 92~100% | 91~100% |
| 구간 뒤 첫 텍스트 스텝 KL(교사 대비): 잠재 KV 있음 / 위치 건너뜀 | 3.36 / 3.42 | 3.45 / 3.44 |
| 같은 스텝 top-1 일치: 잠재 KV 있음 / 위치 건너뜀 | 37% / 32% | 32% / 29% |

- 학습 없는 항등 링크에서는 코어 반복이 구간 시작 상태 근처의 고정점으로 수렴하고(스텝 사이 cos 1.000), 교사
  상태를 따라가지 못합니다. 교사와의 cos는 "시작 상태에 머무는" 기준과 같습니다. 설계 T2(링크 예열)가 필요하다는
  전제와 맞고, T2의 출발 기준값은 위 표입니다.
- 출력 층은 구간의 위치를 KV로 보지 못해도, 올바른 코어 상태만 주면 92~100% 교사와 같은 다음 토큰을 냅니다. 설계의
  가장 큰 리스크("출력 그룹이 잠재 위치를 직접 못 봄", A5)는 코어 상태가 교사에 가까워지면 크게 줄어든다는 뜻입니다.
  다만 이 수치는 구간이 16위치이고 출력 층이 구간 앞 텍스트를 모두 본 조건입니다.
- `last_loop`와 `per_loop`의 차이는 작습니다(구간 뒤 top-1 37% 대 32%, 잡음 범위로 봅니다).
- 원자료: `bench/hybrid/h04_continuity_{lastloop,perloop}.json`, 실행 기록 `bench/hybrid/h04_run.log`.

## H-01 `last_loop` 품질 기준선 (2026-10-19)

같은 가중치(`nvfp4-r4-fp8s`)에 KV 모드만 바꿔 순차 decode로 품질 묶음을 쟀습니다(추론 끔, greedy).

| KV 모드 | GSM8K | HumanEval | MMLU-Pro | 16K 검색 | 묶음 | BF16 대비 |
|---|---|---|---|---|---|---|
| `per_loop` | 88.5 | 85.4 | 42.8 | 90.0 | 76.67 | 97.7% |
| `last_loop` | 91.0 | 82.3 | 42.8 | 100.0 | 79.03 | 100.7% |

- `last_loop` decode는 전체 재계산과 같지 않은 근사지만(`docs/dory_stage0_reference_20261019.md`), 품질 묶음은 떨어지지
  않았습니다. 과제별 차이(HumanEval -3.1점, GSM8K +2.5점, 16K 검색 +2문항)는 작은 묶음의 잡음 범위로 봅니다.
- **판정 G1(제안):** 가정 A1 통과. 하이브리드 설계대로 `last_loop`를 씁니다. 다만 현재 wavefront(91.35 tok/s)는
  `per_loop`만 지원하므로, 텍스트 속도를 지키려면 H-02(`last_loop` wavefront)가 다음 일입니다. `last_loop` 순차 속도는
  E-01에서 `per_loop`보다 1~2% 느렸습니다.
- 원자료: `bench/eval_runs/nvfp4-r4-fp8s-{sequential,lastloop-sequential}-h01`, `bench/results/eval_h01.log`.

## H-03 상태

다른 세션이 CPU 작업을 계속 돌려(CPU 유휴 26~60%) 깨끗한 측정을 아직 못 했습니다. 부하 아래 예비값(같은 실행 안 비교,
2K): 텍스트 스텝 43.3 steps/s, 잠재 스텝 코어 1회 128.9, 2회 68.0 steps/s(약 3.0배, 1.6배). 이 하네스의 텍스트 스텝은
CPU 부하에 더 크게 흔들리므로 배율은 실제보다 높을 수 있습니다.
