# 3단계: GEMV 파리티 규명과 실제 개선 (2026-10-18)

`ksc_gemv_coalesced`가 CPU 참조와 맞지 않던 원인을 찾았다. 원인은 메모리
트랜잭션도 산술 집약도도 아니고 **바이트 순서**였다.

## 원인: Apple GPU의 uint 로드는 little-endian, KSC 레이아웃은 MSB-first

`reinterpret_cast<const device uint*>(codes)` 로 한 워드를 읽으면 Apple GPU는
리틀엔디언 정수를 준다. 커널은 `(w >> (30 - 2c)) & 3` 으로 MSB부터 코드를 뽑았으므로
실제로는 **바이트가 뒤집힌 순서**로 코드를 읽었다.

진단 과정에서 확인한 것:

| 항목 | 결과 |
|---|---|
| `shared_x` 스테이징 | 정확 (GPU x[16] = -0.533, Python -0.5329) |
| GPU가 읽은 word 0 | `0xbad4fa00` |
| Python bytes[0:4] big-endian | `0xe2f9d4ba` |
| Python bytes[0:4] little-endian | `0xbad4f9e2` |

즉 GPU 값은 리틀엔디언 해석과 일치했다. `__builtin_bswap32`를 넣자 파리티가
통과했다(최대 절대 오차 2.86e-06, 허용 1e-3).

이 버그는 2단계에서 고친 스테이징 stride·그룹 매핑과 별개이며, 그때는 드러나지
않았다. 파리티를 CPU 기준으로 잡았기 때문에 이번에 찾을 수 있었다.

## 성능: 1.74배 개선, 그러나 uzu와는 여전히 큰 격차

5회 반복 측정(파리티 유지 상태):

| 커널 | GB/s |
|---|---:|
| 기존 `ksc_gemv_k4096` (1바이트, 행당 SIMD 그룹 1개) | 13.2–15.0 (중간값 14.7) |
| 새 `ksc_gemv_coalesced` (uint 로드, 8행/스레드그룹, 공유 x) | 23.4–26.3 (중간값 24.6) |
| uzu 디코드 실효 (실제 9B 모델) | 261–354 |

새 커널이 **1.67–1.74배** 빠르다. 어드바이저가 예상한 200 GB/s에는 미치지 못한다.

## 왜 200 GB/s에 못 미치는가

측정된 24.7 GB/s는 약 **98.8 G MAC/s**다. M5 Pro GPU의 fp32 처리량(5–8 TFLOP/s)
대비 1% 수준이므로 연산 병목이 아니다. 병목은 **스칼라 의존 사슬**이다.

레인마다 8워드 x 16코드 = 128 MAC을 직렬로 수행하고, 매 반복마다 shared 메모리
로드와 4엔트리 테이블 선택이 붙는다. 한 워드 처리에 약 6–8 명령이 들어간다.

uzu는 같은 바이트를 MMA fragment에 넣어 한 번의 로드로 타일 전체를 처리한다.
즉 **응집 로드만으로는 부족하고, LUT 조회를 정수 연산으로 바꾸고 코드를 fragment
레이아웃으로 재배치하는 작업이 필요하다.** 어드바이저의 두 제안(응집 로드 +
행 타일링) 중 첫째는 성과가 있었고, 둘째만으로는 200 GB/s가 나오지 않았다.

## 이번에 확정한 것

- `ksc_gemv_coalesced`는 파리티 게이트에 포함됐다(5종 -> 6종).
- 기존 커널보다 1.7배 빠르다. 이 수치는 파리티가 있으므로 인용 가능하다.
- 200 GB/s는 재현되지 않았다. 다음 병목은 스칼라 코드 추출이다.
