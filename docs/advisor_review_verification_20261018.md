# 어드바이저 검토 결과 검증 (2026-10-18)

외부 검토가 `docs/problem_report_20261017.md`의 두 진단을 교정했다. 이 문서는
각 주장을 이 저장소의 코드로 확인한 결과를 기록한다. 확인된 것은 반영했고,
확인되지 않은 것은 근거와 함께 남긴다.

## 1. 인코더: 확인됨, 코드가 실제로 해결된다

### 무엇을 확인했는가

`ksc_encoder_b64.py`를 `src/omegahee_ksc_encoder.py`로 통합하고 실행했다.

- block 2~6에서 기존 정확 참조(`omegahee_pillars.ksc_curvetq_quantize_row`)와
  **비용과 코드가 완전히 일치**한다(beam_width = 4^block). 이것이 정확성의
  핵심 증거다.
- block 64에서 실제로 동작한다. 16행 x 64열 기준 MSE 0.121, 비용 벡터, 패킹,
  14비트 헤더를 모두 반환한다.
- `tests/test_omegahee_ksc_encoder.py` 6개 테스트가 이를 고정한다.

즉 **문제 1의 `block <= 6` 제한은 해소 가능하다**는 주장이 옳았다. 이 저장소가
확인할 수 있었던 가장 큰 진전이다.

### 그러나 어드바이저가 인용한 코드는 이 저장소에 없다

검토는 `ksc_curvetq_quantize_row(..., max_k=4)`의 `err_cand` 정의 충돌을
지적했다. 그러나 이 저장소와 GitHub 원격 어디에도 `max_k`나 `err_cand`는 없다
(`git log -S`, 전체 grep, 원격 raw 파일 해시 대조로 확인). 현재 구현은
`curvature_path_cost`가 `err = w - hat`을 쓰고, Viterbi가 같은 함수를 비용
계산에만 호출한다. 즉 **지적된 피드백 불일치가 존재하지 않는다.**

따라서 "반드시 `err[j] = w[j] - q_cand`로 통일해야 한다"는 처방은 적용 대상이
없다. 다만 새 패치 인코더는 `new_err[:, :, j] = W_block[:, j] - chosen_q`로
정확히 그 규약을 쓰고 있으며, 이는 옳은 구현이다.

### 패치 인코더에서 실제로 발견한 버그

`pack_ksc_codes_b64`가 코드 c를 `col_b = col_a + 32` 위치에 넣었다. 이는
uzu 트렐리스의 분할 레이아웃이지 KSC 참조 레이아웃이 아니다. KSC 참조는 코드
c를 연속 비트 `[2c, 2c+1]`에 둔다. 두 레이아웃의 패킹 결과가 다르므로
(`1b1b...` 대 `05af...`), 패치를 그대로 쓰면 커널이 다른 값을 디코드한다.
**패커를 KSC 레이아웃으로 고쳤고**, 왕복 테스트가 통과한다.

## 2. GEMV 대역폭: 교정 가설을 시험했으나 검증에 실패했다

### 어드바이저 가설

51.6 GB/s의 원인은 산술 집약도가 아니라 **1바이트 비응집 로드**다. 레인 0과 1이
같은 바이트를 읽고, SIMDgroup이 스텝당 16바이트만 패치하므로 128B 트랜잭션의
12.5%만 쓴다. 4바이트 응집 로드 + 행 타일링으로 200+ GB/s가 가능하다.

### 시험

`ksc_gemv_coalesced`를 작성했다. 레인당 `uint`(4바이트, 16코드) 로드, threadgroup
공유 x 벡터, 256스레드 그룹당 8행 구조로 가설이 요구하는 조건을 모두 넣었다.

### 결과: 가설은 검증되지 않았다

파리티가 맞지 않는다. 1행 소케이스(N=1, K=256)에서 CPU 기대값 -4.099 vs GPU
-15.382다. 확인한 것과 확인하지 못한 것:

| 항목 | 결과 |
|---|---|
| `shared_x` 스테이징 | **정확**(x와 비트 단위 일치) |
| 행 오프셋, word→code 인덱싱 | 서면 검토상 정확 |
| 레인별 부분합 | Python 재현과 불일치 |
| 스테이징 stride 하드코딩(256) | 버그였음, `group_threads`로 수정 |
| 그룹/행 매핑(gid/32 vs 256스레드) | 버그였음, 고정 그룹 기하로 수정 |
| 남은 원인 | **미규명** |

두 개의 실제 버그를 고쳤지만 값이 여전히 틀린다. 원인을 더 좁히려면 커널 내부
중간값을 단계별로 덤프해야 한다.

따라서 **26 GB/s라는 수치는 인용하면 안 된다.** 파리티가 없는 수치다. 커널은
코드에 남겨 두되, 파리티 게이트에서 분리하고 `verified: false`로 표시했다.

### 어드바이저 가설을 반박하는 정황

- 같은 파일의 `ksc_gemv_k4096`(1바이트 로드, 51.6 GB/s)와 `ksc_decode_simd`
  (32레인 니블 읽기, 파리티 통과) 모두 1바이트 계열인데, 후자는 수락 기준을
  통과했다. 즉 1바이트 로드가 곧 파리티 실패를 뜻하지는 않는다.
- 12.5% 트랜잭션 효율 가설이 맞다면, 응집 커널은 파리티가 맞든 틀리든
  대역폭이 8배로 뛰어야 한다. 실제로는 51.6 → 26 GB/s로 **느려졌다**.

느려진 이유는 추정 가능하다. 레인당 16코드를 해석하는 직렬 루프가 길어졌고,
256스레드 그룹이 4096개 float를 스테이징하는 비용이 행 수가 적을 때 상각되지
않는다. 이는 "응집 로드만으로 200 GB/s"가 성립하지 않음을 시사한다.

## 3. 어드바이저 제안 중 반영한 것과 보류한 것

반영:

- 64열 인코더(문제 1) — 실제 코드로 통합, 정확성 검증됨
- 패커 레이아웃 교정 — 실제 버그였음
- 품질 기준 제안(문제 3): WikiText-2 PPL을 1차, MMLU 5-shot을 최종 지표로
  문서에 기록. 인코더가 안정화된 뒤 측정한다.
- uzu 포크 정책: 커밋 고정, budget 변경만 upstream PR 후보로 분리
- 문제 6(비-Apple 이식성) 보류 동의

보류:

- GEMV 200+ GB/s 달성 — 파리티 미검증이므로 성능 주장 불가
- budget 실측 — 여전히 최우선이지만 이번 작업 범위 밖이었다

## 4. 다음 작업 (우선순위 유지)

1. **budget 3~4 실측** — 가장 저렴하고 예측을 즉시 판정한다(변경 없음).
2. **GEMV 파리티 규명** — 남은 미규명 원인을 찾기 전에는 처리량 논의 불가.
   커널 내부 중간값 덤프로 레인별 코드 워드를 CPU 기대와 대조하는 것이 다음 수순이다.
3. **인코더로 실제 모델 1개 레이어 변환** — 이제 가능하다.
